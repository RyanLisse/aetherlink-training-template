# [TRAINING] fictional redaction bug reproduction exercise — seeded hypothesis

## Scenario and user story

As the fictional Northstar privacy reviewer, I want to check the response
allow-list against a request containing an internal note so that a learner can
distinguish a real observation from a seeded bug hypothesis.

This ticket is deliberately a **bug reproduction exercise**. `REQ-005` is a
negative control: its input row contains `internal_note`, while its expected
public result omits that field. The scenario seeds the hypothesis that an
implementation might leak it. It does **not** prove a bug in the starter,
trainer reference, or any real system. Do not write “bug confirmed” unless a
human observes that exact output in a bounded local run.

## Numbered tasks

1. Read `data/requests.json`, `training-lab/status.py`, the Day 2 Exercise 3 review instructions, and the current diff.
2. Run the existing tests and the supplemental runner from a clean enough local context to identify actual behavior.
3. Inspect `REQ-005` input and compare the observed result's keys with `public_fields` and `redaction_negative_control.expected_output_excludes`.
4. If a leak is observed, record the exact command, output, revision, and reproduction steps as `OPEN` for human review; do not silently fix it here.
5. If no leak is observed, record that the seeded hypothesis was not reproduced. In either case, classify the outcome as observed, not inferred.
