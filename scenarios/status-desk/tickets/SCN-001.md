# [TRAINING] fictional Fictional Reconciliation Demo Support Desk epic

## Scenario and user story

As a support learner in the fictional Fictional Reconciliation demo, I want a shared local
story and synthetic records so that I can practice intent, implementation,
review, and handoff without customer data or external systems.

Fictional Reconciliation is a fictional name for this workbook. This epic makes no claim
about Worldline, a real customer, a real support desk, payment processing, or
production operations.

## Numbered tasks

1. Read the existing [Day 1 guide](../../../days/day-1.md), [Day 2 guide](../../../days/day-2.md), and [status lab README](../../../training-lab/README.md).
2. Read [`data/records.json`](../data/records.json), [`data/requests.json`](../data/requests.json), and [`data/monitoring.json`](../data/monitoring.json).
3. Keep all work inside a learner checkout; do not modify the supplied training-lab fixtures for this scenario setup.
4. Use the ticket links in ID order and let actual command output decide whether an acceptance item is complete.

## Exact files and commands

Files to read: `days/day-1.md`, `days/day-2.md`, `training-lab/README.md`,
`scenarios/status-desk/data/*.json`.

From the repository root:

```sh
python3 --version
python3 scenarios/status-desk/run_requests.py
```

The runner is expected to report failures while the starter API raises
`NotImplementedError`; that is a training state, not a result to mark as
passed.

## Sample expected result

The scenario contains 12 rows and 5 requests. After the learner implements
the API, the runner should print one `PASS` or `FAIL` line per request and a
summary. The exact observed output must be captured by the human reviewer.

## Acceptance criteria

- [ ] The learner can name the fictional boundary and the two public API functions.
- [ ] The supplemental fixtures are loaded without changing `training-lab/records.json`.
- [ ] No customer, vendor, credential, network, deployment, or production claim appears in the work.
- [ ] Ticket order and dependencies are understood by a human facilitator.

## Evidence required and human role

Evidence: the two guide paths read, the root-relative commands run, the exact
runner output, and a readback of the diff or file list. The human facilitator
owns scope; an agent may report commands but cannot mark this epic accepted.
